0.1 · The problem

With no checks, anyone who knows the URL can delete user 42

the endpoint you wrote last week
app.delete("/users/:id", async (req, res) => {
  await db.users.delete(req.params.id);
  res.status(204).end();
});
a stranger, no login, no token
$ curl -X DELETE https://api.shop.example/users/42

HTTP/1.1 204 No Content   // user 42 is gone
  • The code works. It does exactly what it says, for whoever calls it.
  • bugThe server never asked who sent the request, or whether they may do this.
  • 1Who are you? A logged-in admin, a customer, or nobody?
  • 2May you do this? Delete this user, right now?
  • Every request must answer both questions before it touches the database.

0.2 · AuthN vs AuthZ

Authentication finds out who you are. Authorization decides what you may do.

AuthN · authentication
Who are you?

You prove an identity: a password, a 6-digit code from your phone, or "Login with Google".

Result: the server knows user_id = 42, or it knows nothing.

POST /login  { "email": "an@shop.vn", "password": "…" }
→ 200  Set-Cookie: sid=9f2c…   // now we know: user 42
Hotel: the front desk checks your ID card before giving you a key.
AuthZ · authorization
What may you do?

The server knows who you are and checks the rules: a viewer may list users but may not delete them.

Result: allowed, or refused.

DELETE /users/7   // user 42, role: viewer
→ 403  // viewers may not delete users
Hotel: your key card opens room 702, not 703, not the staff room.

orderAuthN always runs first. You cannot decide what someone may do before you know who they are.

0.3 · 401 vs 403

401 means "log in first". 403 means "logging in again will not help".

no token at all
GET /admin/users
(no Cookie, no Authorization header)

HTTP/1.1 401 Unauthorized
  • AuthN failed. The server does not know who you are: token missing, expired, or fake.
  • The name is misleading. It really means unauthenticated.
  • clientSend the user to the login page.
valid token, role: viewer
GET /admin/users
Authorization: Bearer eyJhbGciOiJIUzI1NiJ9…

HTTP/1.1 403 Forbidden
  • AuthZ failed. The server knows you are user 42, a viewer, and viewers may not do this.
  • Logging in again gives the same user and the same answer.
  • clientShow "You don't have access". Don't redirect.

common bugReturn 401 to a logged-in viewer and the frontend sends them to login, they log in, hit 401 again: an endless loop.
