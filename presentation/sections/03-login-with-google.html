3.1 · Why not just ask for the password?

An app that has your Google password has all of Google, until you change it

calapp.vn/connect
CalApp

Connect your Google Calendar to see your week.

Connect
  • everything With the password CalApp can read Gmail, delete Drive files and change your recovery phone. Not just the calendar.
  • no undo You cannot take access back from CalApp alone. Changing the password logs out every app and device you own.
  • one more leak CalApp now stores your Google password. Its database leak becomes your Gmail leak.
  • what we want Read the calendar only · take it back per app · the password never leaves Google.

3.2 · OAuth 2.0 · four roles

OAuth 2.0 hands the app a key that opens one thing, instead of your password

resource owner
You

Own the calendar. The only one who can say yes.

client
CalApp

Wants to act for you. Registered with Google, so it has a client_id and a client_secret.

authorization server
accounts.google.com

Checks your password, asks "allow CalApp?", hands out tokens.

resource server
Calendar API

Holds the data. Answers only a valid token with the right scope.

master key = your password

Opens the doors, the trunk and the glovebox. Hand it to the valet and you handed over the car.

valet key = access_token with scope=calendar.readonly

Starts the engine and nothing else. It expires, and you can take it back any time in your Google account.

3.3 · Authorization Code flow

The password goes only to Google. The app gets a one-time code and trades it for a token.

1 · redirect to Google 2 · log in + Allow 3 · back with a code 4 · code → token 5 · call the API

SPA or mobile app? It cannot hide a client_secret, so it adds PKCE: a random one-time proof sent in place of the secret.

3.4 · OAuth is not login · OpenID Connect

An access token says what the app may do, not who you are. OIDC adds an id_token for that.

OAuth 2.0 · scope=calendar.readonly
access_token: ya29.a0AfH6SMB…

Means "whoever holds this may read a calendar". It does not say whose, and your app is not meant to open it.

OpenID Connect · scope=openid email profile
access_token + id_token

A JWT about the user, made for your app. This is what "Login with Google" really is: OAuth plus one extra token.

  • don't Log users in with an access_token. A token some other app got for that user would work on yours too.

  • store Key the user by sub, not email. A Google email can change; sub never does.

3.5 · MFA · multi-factor authentication

A stolen password is not enough when login also needs a second factor of a different kind

Something you know

password, PIN

Something you have

phone, security key

Something you are

fingerprint, face

Two factors must be two different kinds. Password + security question is still one factor: both are things you know.

Second factorHow it worksWeak spotVerdict
TOTPGoogle AuthenticatorPhone and server share a secret. Both turn the clock into a 6-digit code, new every 30 s. Works offline.A fake login page can ask for the code and use it within 30 s.good default
SMS OTPcode by text messageThe server texts a 6-digit code to your phone number.SIM swap: an attacker talks the carrier into moving your number to their SIM.weakest
Passkeyfingerprint / faceYour device signs a challenge with a private key. It only answers the real domain.Nothing to type, so nothing a fake page can steal.strongest
  • MFA is AuthN It happens at login. With "Login with Google", Google asks for the second factor. Your app never sees it; it just receives the id_token.
