4.4 · What is inside the token

The token says who is calling, for whom, and what it may do

access_token · decoded payload
eyJhbGciOiJSUzI1NiIsInR5cCI6IkpXVCJ9.eyJpc3Mi…
{
  "iss":   "https://auth.shop.internal",
  "sub":   "orders-service",
  "aud":   "payments-service",
  "scope": "payments.charge",
  "iat":   1791943200,
  "exp":   1791943500
}
  • iss who made it. Payments only trusts its own auth server.
  • sub who is calling. A service name, not a user.
  • aud who it is for. Payments rejects tokens made for anyone else.
  • scope what it may do. Charge cards, nothing more.
  • exp when it dies. 300 s after iat. A stolen token is dead in 5 minutes.
  • same JWT as section 2Header, payload, signature. Anyone can read it, so no secrets inside.

4.5 · Validate, then authorize

Payments checks the token, then the scope

step 1 · validate
Is this token real, and meant for me?
  • Signature matches the auth server's public key
  • iss is https://auth.shop.internal
  • aud is payments-service
  • exp is still in the future
verify(token, { issuer, audience: "payments-service" })
// any check fails → 401 Unauthorized
step 2 · authorize
May this caller do this?
  • payments.charge → POST /charges
  • payments.read → GET /charges/*
  • Orders has payments.charge only, so it cannot list charges.
if (!claims.scope.split(" ").includes("payments.charge"))
  // valid token, wrong scope → 403 Forbidden

slide 0.3Same split as for users: 401 = we don't know who you are, 403 = we know, and the answer is no.

4.7 · Other options

Other ways services prove who they are

mTLS · mutual TLS
Both sides show a certificate

Normal HTTPS: only the server proves who it is. With mTLS the caller shows a certificate too.

Identity is checked when the connection opens, before any request is sent.

Cost: someone has to issue and renew a certificate for every service.
service mesh · Istio, Linkerd
mTLS, done for you

A small proxy (a "sidecar") runs next to every service and handles the certificates.

Your code keeps making plain HTTP calls.

Fits many services and a platform team. One more system to run.
API keys
Fine for simple third-party APIs

Stripe, SendGrid, Google Maps hand you a key. Keep it in a secret manager, one per environment.

Not for your own services: no expiry, no scope, no identity.

Rotate it when it leaks or someone leaves.
OAuth = how you get the token· JWT = what it looks like· Payments' policy = what you may do
