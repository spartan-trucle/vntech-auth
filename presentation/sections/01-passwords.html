1.1 · Storing the password as-is

A leaked database must not leak passwords

the obvious first version
CREATE TABLE users (email TEXT, password TEXT);

shop=> SELECT email, password FROM users;
       email        | password
--------------------+-----------
 an@shop.vn         | 123456
 binh@shop.vn       | 123456
 chi@shop.vn        | hunter2
 dung@shop.vn       | Dung@1998
  • Anyone who sees this table sees every password: a backup left on S3, a SQL injection, a teammate with read access.
  • worsePeople reuse passwords. Dung's Dung@1998 probably also opens her Gmail and her bank app.
  • ruleNever store the password itself. Not even "just in dev": dev databases get copied to laptops and shared in Slack.

1.2 · Encryption is not hashing

Encryption can be undone with a key. A hash cannot be undone at all.

Encryption · two-way
Lock it, unlock it later

The key has to live on the server that reads the database. An attacker who gets one usually gets both.

Use it for data you must read back: a partner's API key, a bank account number.

encrypt("hunter2", key) → "q7Zt2V0kN1xR…"
decrypt("q7Zt2V0kN1xR…", key) → "hunter2"
Hashing · one-way
Same input, same fingerprint

Login hashes what the user typed and compares it with the stored hash. Same hash means same password.

Use it for passwords. You never need to read a password back, only check it.

sha256("hunter2") → "f52fbd32b2b3…26a3f6c7"
// there is no unhash()

rulePasswords get hashed, never encrypted. But as the next slide shows, not with sha256.

1.3 · A fast hash is not enough

With SHA-256, the same password gives the same hash, and attackers already have a lookup table

plaintext→SHA-256→+ salt→bcrypt
users · password_hash = sha256(password)
emailpassword_hash
an@shop.vn8d969eef6eca…3adc6c92
binh@shop.vn8d969eef6eca…3adc6c92
chi@shop.vnf52fbd32b2b3…26a3f6c7

An and Binh have identical hashes, so they have identical passwords. Crack one, you have both.

rainbow table · precomputed hash → password
# billions of common passwords, hashed once, shared online
8d969eef6eca…3adc6c92  →  123456
5e884898da28…1d1542d8  →  password
65e84be33532…e02337c5  →  qwerty
  • 0 s123456 is not cracked, it is looked up.
  • SHA-256 and MD5 are built to be fast. One gaming GPU tries about 10 billion hashes per second.
  • Every 8-letter lowercase password: 26⁸ ≈ 209 billion guesses ≈ 21 seconds.

1.4 · Salt

A random salt per user makes the same password hash differently every time

plaintext→SHA-256→+ salt→bcrypt
users · password_hash = sha256(salt + password)
emailsaltpassword_hash
an@shop.vnf3a9c1e07b2d48985a03e88d…5328e99e
binh@shop.vn8e41d6b5a09cb70f4e40345e…ac8b4ffc
 
sha256("f3a9c1e07b2d" + "123456") → 48985a03e88d…
sha256("8e41d6b5a09c" + "123456") → b70f4e40345e…

Both still typed 123456. Nothing in the table shows it.

  • Salt = a random string made for each user at signup, stored right next to the hash. It is not a secret.
  • fixedThe rainbow table is useless: nobody precomputed hashes for f3a9c1e07b2d123456.
  • fixedCracking An tells you nothing about Binh. The attacker starts over for every user.
  • stillSHA-256 is still fast. Against one user, the GPU still makes 10 billion guesses per second.

1.5 · Slow on purpose

bcrypt is slow on purpose, and keeps its own salt inside the hash string

plaintext→SHA-256→+ salt→bcrypt
// same "123456", two users, two different strings
an    $2b$12$k3jBwncGilSoviAey6CdyOeo8nfyzo…
binh  $2b$12$q4itdtqtuEUqc.peZwB4.OppfBkbeZ…
bcrypt.compare("123456", stored)  → true  // ~250 ms

One column, no separate salt: compare reads the cost and salt from the string.

  • Cost 12 ≈ 250 ms per hash. A user logs in once and never notices.
  • All 209 billion 8-letter passwords: SHA-256 ≈ 21 s on one GPU. bcrypt ≈ 1,650 years of CPU time.
  • Cost +1 doubles the time. Argon2id is the newer option; same idea.
