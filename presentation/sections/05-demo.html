5.2 · What is running

The server recomputes the signature first, then checks a permission. Never a role name.

demo/src/jwt.ts · trimmed
export function verify(token: string): VerifyResult {
  const parts = token.split('.');
  if (parts.length !== 3) return { ok: false, reason: 'malformed' };
  const [head, body, signature] = parts;
  let header, payload;
  try { header = decode(head); payload = decode(body); }
  catch { return { ok: false, reason: 'malformed' }; }
  // never let the token choose the algorithm: we only speak HS256
  if (header?.alg !== 'HS256')
    return { ok: false, reason: 'alg not allowed' };
  // HMAC-SHA256(secret, head + "." + body) with OUR secret
  const expected = hmac(`${head}.${body}`);
  const given = Buffer.from(signature, 'base64url');
  // same time whether byte 1 or byte 32 differs
  if (given.length !== expected.length ||
      !timingSafeEqual(given, expected))
    return { ok: false, reason: 'bad signature' };
  // … exp in the past → 'expired'
  return { ok: true, payload };
}
demo/src/server.ts · trimmed
function requireAuth(req, res) {
  const auth = authenticate(req); // JWT or cookie
  if (auth.ok) return auth;
  send(res, 401,
    { error: 'Unauthorized', reason: auth.reason },
    { 'X-Auth-Reason': auth.reason });
  return null;
}
function requirePermission(role, permission, res) {
  if (can(role, permission)) return true;
  send(res, 403,
    { error: 'Forbidden', need: permission });
  return false;
}
// GET /admin/users
const auth = requireAuth(req, res);
if (!auth || !requirePermission(
    auth.user.role, 'users:list', res)) return;
401 who are you? 403 I know you. Still no.

5.3 · Guess first

Four requests, four refusals. Guess the status code for each one before we send it.

#RequestStatusWhy
1GET /me with no Authorization headerno token, no cookie 401missing token The server has no idea who you are. Authentication failed.
2viewer's real token → GET /admin/usersrole viewer, needs users:list 403need: users:list It knows exactly who you are. You just aren't allowed. Authorization failed.
3Edit the payload to "role":"admin", keep the old signatureheader and signature untouched 401bad signature The server recomputes the HMAC over the new payload. It no longer matches.
4Header "alg":"none", signature removed{"alg":"none"} . payload . (empty) 401alg not allowed Only HS256 is accepted. A token can't switch its own check off.

401 means "who are you?". 403 means "I know you, and still no".

5.5 · Why the forged token fails

  
Change one byte of the payload and the signature no longer matches. Making a new one needs the secret.

  

    
signature = HMAC-SHA256(secret, header + "." + payload)

# what the server signed at login
payload    {"sub":"viewer@demo.vn","role":"viewer",…}
signature  B4s4ZzKJIa0oOK3xiG-brhOxkQzSZBrs1nMlTJeFugQ

# you edit the payload, keep the signature
payload    {"sub":"viewer@demo.vn","role":"admin",…}

# server recomputes with its own secret
expected   sfutziofUiF5_mB1rG95XLCsEiKUe152k4Qw_xmWsK0
token has  B4s4ZzKJIa0oOK3xiG-brhOxkQzSZBrs1nMlTJeFugQ
           ≠  → 401 bad signature

    
    
      
  • The payload is only base64url, not encrypted. Anyone can read and edit it. The signature is what makes edits detectable.
    • 
      
  • To sign the admin payload yourself, you need the secret. HMAC can't be run backwards to find it.
    • 
      
  • Secret leaked = game over. Anyone can mint an admin token that passes every check, and the server can't tell.
    • 
      
  • Keep it in env (JWT_SECRET), long and random, different per environment. Never commit it. dev-only-secret-change-me is exactly what not to ship.
